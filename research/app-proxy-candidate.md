# 候选方案：应用鉴权转发 COS 素材（专项说明）

> 日期：2026-10-09。状态：**候选方案**，买家尚未同意，也没有取代买家原来的“预签名短期链接”要求。
> 本轮只做设计说明，没有开发、没有购买资源、没有改云权限、没有联系买家。
> 标记说明：❓表示尚未验证；“需复核”表示数据来自官方页面的搜索摘要，没有直接打开原页核对。
> 工时影响要等拿到两个 01 文件的明细后再核对，本文不给工时和价格。

## 1. 方案要点

```
访客浏览器/微信 ──HTTPS──> 香港主机（应用：鉴权 + 转发 + 预览缓存）──内网?──> 香港 COS（私有桶）
管理员浏览器   ──HTTPS──> 香港主机（上传 → 生成预览 → 写入 COS）
```

- COS 桶私有读写，不对外签发任何 COS 地址。只有服务端持有 CAM 子账号密钥。
- 访客输入相册密码后，服务端签发一个**相册会话令牌**。之后每次请求素材，服务端都会校验令牌、所属相册和当前密码版本。校验通过才从 COS 读取（或从主机缓存读取）并返回。
- 本说明另有一条建议：**网格页用的缩略图**（长边约 480 像素，约 40–80 KB）和**大图预览**（长边 1920 像素）分开生成。V3/V4 只规划了一档 1920 像素预览，网格直接用它会让首屏流量放大 5–10 倍（见第 3 节）。

## 2. 缓存与撤销边界

### 2.1 各层能撤销到什么程度

| 层级 | 改密码 / 删相册 / 删照片后 | 说明 |
|---|---|---|
| 服务端鉴权 | **新请求立即拒绝** | 令牌里绑定相册的 `password_version`。改密码时版本号加 1，旧令牌全部失效。删除照片后该照片立即返回 404 |
| 正在传输的响应 | 已经开始的那次传输会传完 | 无法中途撤回；大原图可能还要几秒 |
| 主机上的预览缓存 | 不影响鉴权 | 缓存只在鉴权**之后**读取。删除照片时同步删除缓存。缓存可以随时从 COS 重建 |
| 访客浏览器 / 微信缓存 | **无法撤销**，直到缓存过期或被清掉 | 由响应头控制，见 2.2。微信内核是否严格遵守这些响应头 ❓ |
| 访客已保存的文件 | **无法撤销** | 写明不承诺追回 |
| 被转发出去的素材地址 | 令牌在有效期内可以被第三方使用；改密码后立即失效 | 令牌是持有即可用的凭证。缓解办法见 2.3 |
| CDN | 首期**不接入** CDN | 将来若接入，不能缓存需要鉴权的响应，否则撤销会失效 |

### 2.2 建议的响应头（待真机验证）

| 素材 | `Cache-Control` | 理由 |
|---|---|---|
| 缩略图、预览图 | `private, max-age=600` | 减少重复浏览产生的主机流量；撤销后最多还有 10 分钟残留在访客本机缓存 |
| 原图 | `private, no-store` | 不在中间环节留副本。微信长按保存时会怎么重新取图，需要实测 ❓ |
| 音乐 | `private, no-store`，支持分段请求（Range） | 保证拖动进度和续播；令牌在会话期内有效，不会出现 5 分钟链接中途过期断播的问题 |

- 所有响应都加 `Referrer-Policy: no-referrer`，避免令牌通过 Referer 泄露出去。服务器日志里要脱敏令牌。
- 换图时使用新的对象键（照片 ID + 版本号），避免访客缓存里新旧图混在一起。

### 2.3 令牌的绑定方式（两种互相权衡）

- **只用 Cookie 会话：**素材地址被转发出去也打不开，最安全。但微信长按保存时可能由微信自己重新下载，**不带网页的 Cookie**，原图可能因此保存失败 ❓。
- **建议的折中做法：**
  - 网格、预览、音乐用“Cookie 会话 + 地址中的令牌”双重校验。
  - 只有“单张原图保存”这一个接口，签发一个**单张、短时效的地址令牌**（例如 10 分钟，只对这一张照片有效）。
  - 改密码后，原图令牌同样立即失效。
  - 这一设计必须经过 iOS 和 Android 微信真机验证才能定稿 ❓。

### 2.4 会话参数

- 相册会话 2 小时，到期后重新输入密码。管理员可以对单个相册执行“全部下线”，效果和改密码一样，都是版本号加 1。
- 不再需要“5 分钟链接、剩余不足 1 分钟续签”的机制。原因是每次请求都在服务端鉴权，撤销已经是即时的。

## 3. 主机流量与费用

### 3.1 流量走向和计费方

| 路段 | 应用转发 | COS 预签名直连 |
|---|---|---|
| 访客 ← 服务端 | **主机公网出流量**，计入套餐流量包，超出部分按量计费 | 只有页面和接口，流量很小 |
| 服务端 ← COS | 同地域如果走内网：通常不计外网流量费 ❓；如果走公网：**另计 COS 外网下行，相当于付两次钱** | 不经过主机 |
| 访客 ← COS | 无 | **COS 外网下行流量**（香港地域单价未查到） |
| COS 请求次数 | 有预览缓存时，主要是原图和音乐的读请求 | 访客每次加载都算一次读请求 |

**已查到的单价（需复核）：**

| 计费项 | 单价 | 来源 |
|---|---|---|
| 轻量服务器中国香港套餐外流量 | **1.0 元/GB**（只计公网出方向） | 官方《价格总览》，经搜索摘要获得 |
| COS 中国香港标准存储 | 0.136 元/GB/月 | 2024 年降价通知 |
| COS 香港外网下行流量 | 未查到 | — |
| COS 香港读请求 | 未查到 | — |
| 轻量服务器各套餐包含的月流量和带宽上限 | 以购买页为准 | — |

**必须实测的一项 ❓：**在主机上运行 `nslookup <桶名>.cos.ap-hongkong.myqcloud.com`，看是否解析到内网 IP；再对照第一个月的账单，确认没有产生 COS 外网下行费用。官方文档只给出了 CVM 的判断方法，没有针对轻量服务器的明确条款。

**如果确认走不了内网，降低风险的办法：**把全部缩略图和预览图常驻在主机磁盘上（COS 仍是原始存储，缓存可以重建）。按 5000 张估算，缩略图约 0.3 GB，预览图约 1.5 GB，这样 COS 只需要为原图和音乐向主机出流量。

### 3.2 月流量估算公式与示例（不是报价）

> 月流量 ≈ 打开相册次数 ×（首屏缩略图 + 实际翻看的预览图 + 音乐播放比例 × 单首大小）+ 原图保存次数 × 平均原图大小

以下示例假设：每次看 30 张缩略图（每张 60 KB）和 20 张预览图（每张 350 KB），音乐 5 MB、播放率 50%，原图平均 8 MB，不计浏览器缓存带来的节省。

| 场景 | 每月打开相册次数 | 每月原图保存次数 | 约计月流量 | 超出套餐流量时的参考费用（1.0 元/GB） |
|---|---|---|---|---|
| 低 | 300 | 100 | 约 4.1 GB | 先扣套餐内含流量；超出部分 × 1.0 元/GB |
| 中 | 2,000 | 600 | 约 27 GB | 同上 |
| 高 | 10,000 | 3,000 | 约 134 GB | 同上 |

计算方法：每次打开相册约 1.8 MB（缩略图）+ 7 MB（预览图）+ 2.5 MB（音乐）≈ 11.3 MB；按 1 GB = 1024 MB 换算。

套餐内含多少流量，要以买家下单时的套餐为准。上表只说明量级，不能当作费用承诺。

### 3.3 带宽是体验瓶颈

- 峰值带宽为 X Mbps 时，主机最大出口速度约为 X÷8 MB/s，所有访客共享。以 30 Mbps 为例，约 3.75 MB/s：
  - 10 人同时打开首屏（每人约 0.6 MB 缩略图）：约 2 秒；
  - 单张 15 MB 原图独占带宽时约 4 秒，同时有人浏览时会更慢。
- 所以必须做三件事：网格用缩略图；预览图懒加载（滚到才加载）；原图只在用户点击保存时才传输。
- 如果原图保存很频繁，体验和流量都会受限，这时可以考虑第 5 节的“混合方案”。

## 4. 压缩失败与重启恢复

### 4.1 照片处理状态

```
uploading ──原图写入 COS 成功──> pending ──开始处理──> processing ──成功──> ready（访客可见）
     │                               ▲                       │
     └─上传中断→ 清理临时文件          └────暂时性失败（重试≤3次）─┤
                                                             └─永久失败→ failed（显示原因，管理员可重试或删除）
```

- **ready 之前访客看不到这张照片**，也绝不会因为压缩失败就把原图公开出去作为替代。
- 处理任务记录在 SQLite 任务表里（开启 WAL 模式），字段包括：照片 ID、版本号、状态、已尝试次数、下次重试时间、租约到期时间、错误原因。
- 处理在应用进程内的后台线程中进行，并发数为 1–2，防止内存不足。Pillow 保持默认的解压炸弹保护。上传前就校验文件不超过 20 MiB、不超过 4000 万像素。

### 4.2 区分失败类型

| 类型 | 例子 | 处理方式 |
|---|---|---|
| 暂时性失败 | COS 超时、网络抖动、主机内存一时不足 | 退避后重试，最多 3 次。仍然失败就转为 failed，并标注“可重试” |
| 永久性失败 | 文件损坏、格式不支持、超出大小或像素上限 | 直接转为 failed，显示原因，不自动重试 |
| 照片在处理期间被删除 | 管理员删除了正在处理的照片 | 写结果前先检查照片是否还存在；已经不存在就删除刚生成的预览，任务直接结束 |

### 4.3 重启和崩溃后的恢复

1. **进程托管：**用 systemd 或 Docker，设置 `restart=always`，开机自动启动。
2. **启动时自检：**
   - 状态为 `processing` 且租约已过期的任务，重置为 `pending`（这类任务是崩溃时没做完的）。
   - 清理残留的临时上传文件。
   - 检查数据库完整性（`PRAGMA integrity_check`）。
3. **处理过程可重复执行：**预览的对象键由“照片 ID + 版本号 + 尺寸”唯一确定。同一个任务重复跑，只会覆盖成相同的结果，不会产生重复数据。
4. **上传顺序：**先把原图完整写入 COS，再把数据库状态改为 pending。如果写 COS 时中断，数据库里会留下一条 uploading 记录，由对账任务清理。
5. **定时对账（例如每天一次）：**
   - COS 里有、数据库里没有的对象，超过 24 小时宽限期后删除。
   - 数据库里状态为 ready、但 COS 里缺失文件的照片，标记为异常并提醒管理员。
6. **数据库备份：**每天把 SQLite 在线备份到 COS 的独立前缀下，保留 N 天。验收时要做一次“删掉主机后从备份恢复”的演练。
7. **主机缓存丢失**（例如换了主机）：缩略图和预览图在访问时按需从 COS 重新生成或重新拉取，不影响正确性。

### 4.4 需要加入验收的项目

- 处理过程中重启进程，确认照片最终变为 ready 或 failed，不会一直卡在 processing。
- 损坏的文件、超过上限的文件，能给出正确的失败原因。
- 故意让 COS 连接失败，确认重试和退避生效。
- 删除正在处理的照片，确认不会留下孤立对象。
- 做一次备份恢复演练。

## 5. 与买家“预签名短期链接”要求的差异

V3/V4 记录的买家要求是：“正确验证相册密码后才能取得短期素材链接”。03 v3 的第 S1 条也注明，那个 5 分钟签名端点是方案自己的设计，并不是 COS 原生的预签名。所以要分清楚：

- 如果买家的原话**明确要求 COS 原生预签名地址**，那么应用转发**不符合字面要求**，必须征得买家书面同意，才能用它替代。
- 如果买家的意思只是“短期、可失效的链接”，应用转发同样能满足，而且撤销更及时。但仍然建议向买家说明两者的差异。

| 对比项 | A. COS 预签名直连（买家原要求） | B. 应用转发（候选） | C. 混合：预览和音乐走转发，原图走 COS 预签名 |
|---|---|---|---|
| 谁签发、谁鉴权 | 服务端鉴权后签发 COS 地址；之后访客直连 COS，COS 只校验签名 | 每次请求都由服务端鉴权 | 两种都有 |
| 改密码后的撤销 | **已签发的地址一直有效到过期**，所以有效期只能很短（如 5 分钟），这就需要续签 | **新请求立即失效** | 预览立即失效；原图地址有效到过期 |
| 地址被转发给他人 | 有效期内可用 | 会话有效期内可用；加 Cookie 双重校验后会更难 | 原图地址在有效期内可用 |
| 长时间轮播、音乐播放 | 地址过期后要换地址，**音乐可能中途断掉**，需要额外开发和测试 | 不受影响 | 不受影响 |
| COS 新桶默认域名强制下载（2024 年起） | **会受影响**：图片能否在网页里正常显示要实测；稳妥做法是绑定自定义源站域名 ❓ | 不受影响（访客不接触 COS 域名） | 原图部分受影响 ❓ |
| 自定义域名是否需要备案 | 香港桶绑定的域名是否要备案，需在控制台确认 ❓ | 只有主机的域名 | 同 A |
| CORS 配置 | 如果前端用 fetch 取素材，就需要配置 | 不需要 | 视实现方式而定 |
| 访客流量由谁计费 | COS 外网下行（香港单价未查到） | 主机流量（超出套餐 1.0 元/GB，需复核） | 两边分摊 |
| 主机带宽压力 | 小 | 大（见 3.3） | 中，大文件不经过主机 |
| 依赖哪项未验证技术 | 官方 COS SDK 的签名方式基本是成熟路径；但新桶默认域名、自定义域名和备案都要实测 | 主机能否内网访问 COS 要实测 | 两边都要实测 |
| 微信原图保存 | 微信重新下载时带着签名地址，有效期内可以取到 ❓ | 需要单独的原图令牌（2.3），否则可能因为没带 Cookie 而失败 ❓ | 同 A |
| 实现复杂度 | 续签逻辑 + 域名配置 | 转发 + 缓存 + 令牌 | 最高 |

**结论（供卖家决策，买家尚未选择）：**

- 按本单规模，B 方案撤销最及时，绕开的云端未知项最多，实现也不复杂。代价是访客流量和带宽集中在主机上。
- A 方案符合买家要求的字面意思，但续签、断播和默认域名这几个问题都要解决。
- C 方案只有在“原图保存很频繁、主机带宽明显不够”时才值得采用。
- 三种方案相对 V4 估算工时的增减，要等 01 明细到了再核对。
